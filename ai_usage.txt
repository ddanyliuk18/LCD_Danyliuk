WHAT AN OPTIMIZATION IS
An optimization is a transformation that keeps what a program does and changes how it does it. “What it does”
is everything an observer outside the program can see: the lines it prints, the input it reads, the exit value. The
variables, the functions and the order of the computations are not part of it, so the compiler may change them. C++
writes this down as the as-if rule: an implementation may do anything that gives the same observable behaviour
as the program as written.
The simplest real optimization is removing what has no effect. A C variable nobody reads, compiled by clang
without and with optimization:
int main(void) {
 int unused = 42;
 return 0;
}
; clang -O0 -S -emit-llvm ; clang -O1 -S -emit-llvm
%1 = alloca i32, align 4 ret i32 0
%2 = alloca i32, align 4
store i32 0, ptr %1, align 4
store i32 42, ptr %2, align 4
ret i32 0
At -O0 the variable gets its slot %2 and its store (%1 is the slot clang keeps for the return value); at -O1 both are
gone, because nothing reads them, and the program still exits with 0.
Where an optimization runs. On the tree, where the compiler still knows names, scopes and whole functions;
on the IR, where LLVM’s opt runs passes such as dce (drop an instruction without side effects whose result is
unused) and globaldce (drop an internal function nobody references); and on machine code. The two removals
of this week are done on the tree, by one more visitor that runs after the checker and before code generation. A
function on the tree is one node: removing it removes its body, with every declaration and call inside it, in one cut.
Why it iterates. Removing one thing can make another thing unused. If y is initialised from x and nobody reads
y, then x is read only by a declaration that is about to disappear. The pass repeats until a round removes nothing.
The loop stops, because every round that does not stop removes at least one declaration or function, and there are
finitely many.
When in doubt, keep. An optimization may remove only what it can show nobody observes. A declaration whose
value calls a function may print, so it stays. A pass that keeps too much is merely slow; a pass that removes too much
is a wrong compiler. The check is mechanical: every program prints the same thing with the flag and without it.

THE INTERFACE
One new flag, anywhere on the command line:

Without the flag the compiler behaves exactly as before. With it, the pass runs once the checker has accepted the
program: an optimization never sees an invalid program. --ast-checked then shows what code generation will
get; --ast is still the parse tree.
TASK 1 — UNUSED VARIABLES (1.5 POINTS)
What counts as a use
A variable is used where it is read: in an initialiser, on the right of :=, in a condition, in an argument, in print, in
an exit, at the start of a field chain p.x, as the object of a member call p.sum(), in a capture list [k], as a callable
object in a call c(5). An assignment to it is not a use: y := 5 and p.x := 5 on a y or a p nobody reads are as
dead as the declaration. When a declaration goes, every assignment to that variable goes with it.
A function can print and read, so a call is never safe to drop without knowing more. The rule for this task: a
declaration whose initialiser contains a call or read() stays, even with no reads, and so does an assignment whose
value contains one, together with the declaration of its variable. Calls whose functions really do nothing visible are
the additional task.
The pass
1. One visitor walks the whole tree and builds a table: for every declaration, not every name, the number of reads
that resolve to it. The checker already resolved each name to its declaration; that is what scope and shadowing
mean. Reuse that link: a decl field on every variable node, filled by the checker. If your nodes do not carry it
yet, add it now.
2. Every declaration with zero reads is removed from its block, together with the assignments to it.
3. If something was removed, run the visitor again on the new tree: a read that lived in a removed initialiser is
gone, so another declaration may now be at zero. Stop when an iteration removes nothing.
Declarations at the top level, inside if and while blocks, inside function bodies, member functions and lambda
bodies are all in scope of the pass. Parameters, fields and lambdas are not: a parameter belongs to the function’s
signature, and its callers pass it whether or not the body reads it.

Skeleton
class UseCounter: # one more visitor
 def __init__(self): self.reads = {} # id(decl) -> count
 def visit_decl(self, n):
 self.reads.setdefault(id(n), 0)
 if any(has_call_or_read(e) for e in n.inits): self.read(n) # kept: may print
 for e in n.inits: e.accept(self)
 def visit_var(self, n): self.read(n.decl) # any node with a decl, e.g. p.x
 def visit_assign(self, n): # the target is not a read,
 if has_call_or_read(n.value): self.read(n.decl) # unless the value may print
 n.value.accept(self)
 def read(self, decl): self.reads[id(decl)] = self.reads.get(id(decl), 0) + 1
 ... # every other node: visit the children
def remove_unused(tree):
 while True:
 counter = UseCounter(); tree.accept(counter)
 dead = {d for d, k in counter.reads.items() if k == 0}
 if not dead: return tree
 Pruner(dead).prune(tree) # dead DeclNodes and their :=
Pruner walks every block and rebuilds its statement list without the dead declarations and without the assignments
whose decl is one of them. Rebuild the list; do not delete from a list you are iterating over. Keys are id(node):
two declarations named x are two keys.
Errors and limits
The pass reports nothing to the user: an unused variable is not an error. A variable that only feeds itself,
k := k + 1 with nobody else reading k, survives: the right side reads it. That is a limit of counting, not a bug;
say so in the note.
Typical pitfalls
• Counting by name: the outer x gets the inner x’s read and survives. Count per declaration; the checker already
knows which one a name means.
• Counting the target of an assignment as a read. y := 5 keeps nothing alive.
• Forgetting the assignments: the declaration goes, y := 5 stays, and code generation meets a name without
a slot.
• Removing parameters. A function that ignores an argument still has that parameter; its callers pass it.
• An if whose block becomes empty. It stays: its condition is still evaluated, and code generation must accept an
empty block.
• Parsing the flags in a fixed position: they may come first, last, or between the paths.
• Running the pass before the checker: names are not resolved yet, and an invalid program could be “optimized”
into a valid one.
TASK 2 — UNUSED FUNCTIONS (1 POINT)
The same shape, one level up. The visitor also counts the calls of every global function, wherever the call stands: in
3
the statements, in another function, in a member function, in a lambda body. A function with zero calls is removed
with its whole body. Then iterate: the removed body may have held the only call of another function. Member
functions and lambdas stay; only global functions are removed.
fn twice := (i32 a) -> i32
{
 i32 r{a + a}
 exit r
}
fn helper := (i32 a) -> i32
{
 exit twice(a)
}
fn unused := () -> i32
{
 exit helper(1)
}
exit twice(2)
Iteration 1 removes unused; iteration 2 removes helper, whose only call
went with it; iteration 3 finds twice still called and stops. The program exits
with 4 before and after, and with the flag the emitted .ll defines only two
functions: the one for twice, and main.
Two functions that call only each other never reach zero calls, so they stay.
Counting cannot see a cycle; the same reason reference counting cannot free
one.

ADDITIONAL TASK — CALLS WITHOUT EFFECTS (+1)
The rule of Task 1 keeps every value that contains a call. Most calls print nothing and read nothing, so the rule
keeps too much. With the additional task, --remove-unused keeps a value only if it contains read() or a call of
a function that has an effect:
• a function whose body contains print or read();
• a mutating member function: it changes the object it is called on;
• a function that may not return: its body has a while, or it calls itself, directly or through other functions (a call
that never returns is observable: the program hangs);
• a function that calls a function with an effect.
The last rule is circular when functions call each other, so compute the set as a fixpoint: start from the first three
rules and add callers until nothing changes. A callable object’s call is the call of its call. Removals now feed each
other: a removed declaration can take away the only call of a function.
fn square := (i32 a) -> i32
{
 i32 r{a * a}
 exit r
}
fn quiet := (i32 a) -> i32
{
 exit square(a)
}
fn loud := (i32 a) -> i32
{
 print(a)
 exit a
}
i32 a{square(3)}
i32 b{quiet(4)}
i32 c{loud(5)}
exit 0
With Task 1 alone nothing is removed. With the additional task, iteration 1
removes a and b, iteration 2 removes quiet, iteration 3 removes square,
iteration 4 stops. What remains is loud, the declaration of c and exit 0; the
program prints 5 and exits with 0, as before.
A mutating call stays even when its result is unused: in i32 t{c.bump()}
with a bump that adds 1 to a field, t is kept and print(c) still shows
Counter{n: 1}. A peek that only reads the field has no effect, so
i32 u{c.peek()} goes.
